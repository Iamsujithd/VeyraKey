# Task 3 actionable findings

<details>
<summary>Issues (8)</summary>

1. **HIGH — confirmed — Compartment step-up is not bound to the active root session.**
   - **Evidence:** `stepUpCompartment` opens only the requested `document` or `credential` wrapper (`packages/vault/src/service.ts:1488-1503`); it never opens that slot's root wrapper or compares it with the authenticated `rootKey`. Password change, enrollment, Recovery Kit replacement, and drill completion do make that comparison (`service.ts:1109,1246,1348,1669`). A slot replaced in mutable local persistence under an attacker-chosen secret can therefore install an attacker-known compartment key while the legitimate root session remains open.
   - **Remediation:** Open the same slot's root wrapper during every step-up, compare it in constant time with `rootKey`, and reject generically before opening/installing the compartment key on mismatch. Wipe the temporary root in `finally` and add tampered-slot tests for password, Recovery Kit, and PRF step-up.

2. **HIGH — confirmed — Newer headers are accepted without reconciling recovery state, so stale sessions can bypass the Recovery Kit drill gate.**
   - **Evidence:** `requireUnlockedHeader` accepts any V2 header with the same vault ID without comparing/tracking its revision or authenticating its payload (`packages/vault/src/service.ts:1066-1074`). Password change and device enrollment gate on old in-memory recovery state (`service.ts:1082-1086,1210-1214`) and publish `unlockedState(next, true)` (`service.ts:1124,1283`). If instance B replaces the Recovery Kit and commits `recoveryKitVerified: false`, previously verified instance A can read B's newer header, pass its stale gate, enroll a device or change the password, and report recovery as verified. CAS prevents simultaneous lost updates but not this sequential stale-session authorization bypass.
   - **Remediation:** Track the authenticated header revision. On revision change, authenticate the payload with the held root, refresh recovery/device state, and re-run operation gates; lock on reconciliation failure. Reload and publish the winner after CAS conflicts, and derive recovery status from authenticated payload state instead of hard-coding `true`.

3. **MEDIUM — confirmed — Recovery catch-all blocks misreport storage, CAS, and KDF failures as invalid Recovery Kits.**
   - **Evidence:** `restoreVault` performs new-password KDF/wrapping and `repository.create(next)` inside a catch that preserves only `VAULT_ALREADY_EXISTS`; all other failures become `INVALID_RECOVERY_KIT_OR_CORRUPT_DATA` (`packages/vault/src/service.ts:1374-1416`, persistence at line 1409). `verifyRecoveryKit` converts `persistReplacement` conflicts and persistence failures to the same authentication error (`service.ts:1649-1681`).
   - **Remediation:** Map only decode, wrapper-authentication, and payload-authentication/schema failures to the generic recovery error. Preserve KDF policy, persistence/unavailability, and `VAULT_WRITE_CONFLICT`; reload the winner on conflict and expose retryable UI guidance.

4. **MEDIUM — confirmed — Two PRF error paths retain controllable copies of secret PRF output.**
   - **Evidence:** `prfResult` copies the authenticator result and returns `null` for a non-32-byte value without wiping the copy (`packages/crypto/src/index.ts:383-386`). Enrollment validates `enrolled.credentialId` before assigning `enrolled.prfOutput` to the variable wiped in `finally` (`packages/vault/src/service.ts:1247-1249,1289-1292`), so an invalid ID leaves a valid returned output unwiped. The existing test exercises that ordering (`packages/vault/src/task3.test.ts:364-368`) without asserting cleanup.
   - **Remediation:** Zero invalid-length output before returning `null`. Capture `enrolled.prfOutput` immediately after `enroll()` returns, then validate inside `try/finally`; add buffer-zeroing tests for malformed output, invalid/duplicate IDs, wrapping failure, and CAS failure.

5. **MEDIUM — confirmed — Recovery Kit compartment step-up is unreachable in both shipped UIs.**
   - **Evidence:** The client contract and service support `{ type: "recovery-kit" }`, and the vault test proves Recovery Kit document step-up (`packages/vault/src/types.ts:175-178`; `packages/vault/src/task3.test.ts:243-248`). `VaultScreen` submits only a master-password credential (`packages/ui/src/VaultScreen.tsx:350-359`) or PRF. Both web and extension use this component, so a Recovery Kit user without the old password cannot open either sensitive compartment.
   - **Remediation:** Add a Recovery Kit step-up option, submit the existing credential variant, clear it after every attempt, and test both compartments on capability-supported and unsupported surfaces.

6. **MEDIUM — confirmed — Multi-device unlock and step-up always target slot zero.**
   - **Evidence:** Locked-device unlock calls only `slots[0]` (`packages/ui/src/VaultScreen.tsx:639-643`), and device step-up does the same (`VaultScreen.tsx:843-846`), although all active slots are exposed and rendered for revocation at line 881. A usable later credential cannot be selected when the first authenticator is unavailable.
   - **Remediation:** Render a selectable action for each slot with a stable user-recognizable label, or let the provider evaluate all credential IDs with their matching PRF inputs and return the selected slot. Test first-slot failure with second-slot success.

7. **MEDIUM — confirmed — The real-authenticator compatibility release gate has no repository evidence.**
   - **Evidence:** The ADR leaves real-authenticator compatibility as a release gate (`docs/21-architecture-decisions.md:149`). PRF adapter tests use only a mocked `WebAuthnPrfPlatform` (`packages/crypto/src/webauthnPrf.test.ts:15-28`), so they do not validate actual capability reporting, creation-time `enabled`, `evalByCredential`, RP scoping, popup lifetime, or authenticator-specific behavior.
   - **Remediation:** Before marking Task 3 complete, record HTTPS web runs across the supported browser/authenticator matrix for capability, enrollment, assertion unlock, step-up, cancellation, missing extension results, revocation, and fallback. Record extension builds as intentionally unsupported without host permissions.

8. **LOW — confirmed — Failed Task 3 UI operations retain entered secrets in React state and DOM fields.**
   - **Evidence:** `clearSecrets` exists (`packages/ui/src/VaultScreen.tsx:200-211`), but restore, Recovery Kit verification, step-up, enrollment, and password change clear their Recovery Kit/password fields only on success; failure paths leave controlled values mounted (`VaultScreen.tsx:243-424`).
   - **Remediation:** Clear credentials in `finally` or immediately after copying them into the client call. Preserve only non-secret encrypted BYOS text when useful, and add failure-path UI tests.
