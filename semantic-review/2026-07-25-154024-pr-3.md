# Task 3 remediation re-review (v2)

Three actionable defects remain in revision reconciliation and recovery error classification. The blocking issue is that decrypting recovery state proves authenticity but not association with the current header revision, allowing authenticated old state to be replayed. **Watch for:** **HIGH — confirmed** recovery-gate replay; **MEDIUM — confirmed** stale live state after CAS loss; **MEDIUM — confirmed** crypto-unavailability reported as an invalid Recovery Kit.

## High-level view

Reconciliation decrypts the persisted payload before privileged operations, but neither its AAD nor another root-authenticated structure binds the payload to the header revision and mutable slot state. A prior verified payload can therefore be spliced into another revision and accepted as current.

CAS prevents stale persistence from overwriting a winner, but the loser does not reload that winner. Its old recovery status and open compartment keys remain live until a later reconciliation or expiry.

Restore and verification preserve KDF and persistence failures, but their authentication catches still include crypto-provider outages during wrapper/payload opening. Those outages are presented as bad Recovery Kits.

**Documented release gate — not a code defect (confirmed):** real-browser/authenticator matrix evidence remains unavailable and is recorded as a Task 3 release gate in `docs/21-architecture-decisions.md:149`. Collect it before claiming compatibility; it is not counted below.

<details><summary>Details</summary>

## Recovery verification state is authentic but not fresh

**Severity/confidence: HIGH — confirmed.** `aadFor` omits the header revision (`packages/vault/src/service.ts:164-172`), while V2 payload sealing/opening use the constant subject `vault-payload` (`service.ts:66,714-750`). For any unequal revision—including a decrease—`requireUnlockedHeader` decrypts the payload and publishes its `recoveryKitVerified` Boolean as current (`service.ts:1078-1090`).

After Recovery Kit replacement writes `recoveryKitVerified: false`, an older authenticated `true` payload can be copied into that header and still decrypt under the unchanged root key, reopening password change and device enrollment. A lower full-header revision is also accepted, permitting rollback of prior recovery slots or device tombstones.

Add a root-authenticated manifest/tag covering the revision and mutable security metadata, including recovery state/slot identity and device tombstones, and regenerate it for every revision. Reject and lock on revision regression or failed reconciliation. Test old-payload splicing after kit replacement, old payload+slot under a higher revision, lower full-header revisions, and revoked-device rollback.

## CAS conflicts leave the losing session stale

**Severity/confidence: MEDIUM — confirmed.** `persistReplacement` translates and rethrows `VAULT_WRITE_CONFLICT` without reading or publishing the winner (`packages/vault/src/service.ts:852-865`), despite the accepted requirement that stale writers reload committed state (`docs/21-architecture-decisions.md:158`). A concurrent kit replacement or device change can leave the loser exposing old recovery/device state and retaining open compartment keys.

On conflict, read and authenticate the winner against the active root, clear compartments, and publish refreshed state before returning the conflict; lock if authentication or session-generation checks fail. Test a winner replacing the Recovery Kit while a loser with an open compartment loses CAS.

## Recovery catches still collapse crypto outages

**Severity/confidence: MEDIUM — confirmed.** Restore catches every error from kit decoding, wrapper opening, and payload opening (`packages/vault/src/service.ts:1417-1429`); verification does likewise (`service.ts:1723-1737`). HKDF can raise `CryptoError("CRYPTO_UNAVAILABLE")` (`packages/crypto/src/index.ts:95-98`), which both paths replace with `INVALID_RECOVERY_KIT_OR_CORRUPT_DATA`.

Normalize only malformed kit input, authenticated-decryption/key/root failures, and decrypted-schema failures. Preserve crypto-provider operational errors and add injected-unavailability tests for wrapper and payload opening in both flows.
