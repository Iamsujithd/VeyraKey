# Task 3 security hardening re-review (v3)

Two actionable code findings remain. Crypto-provider outages are still converted to credential failures on password/device unlock and shown as credential or data corruption in the UI. Automatic lock and other service-published state transitions leave unsubmitted credentials in React state. **Watch for:** **MEDIUM — confirmed** operational crypto failures are masked; **LOW — confirmed** unsubmitted UI secrets survive automatic lock and flow changes.

**Verdict**: NEEDS_CHANGES

## High-level view

**MEDIUM — confirmed:** Recovery restore and verification preserve `CRYPTO_UNAVAILABLE` at the service boundary, but V2 password/device unlock still normalizes it to authentication failure, and the UI does not distinguish preserved operational errors from bad credentials.

**LOW — confirmed:** Submitted credentials are cleared before asynchronous operations, but unsubmitted secrets survive automatic or conflict-driven lock and method/form switches because only the manual Lock action invokes the shared clearing routine.

## Crypto-provider outages still become credential failures

**Severity/confidence: MEDIUM — confirmed.** In `packages/vault/src/service.ts`, `unlock()` preserves only KDF-policy and unsupported-version `VaultError`s before throwing `INVALID_PASSWORD_OR_CORRUPT_DATA`; `openMasterRoot()` also broadly normalizes failures, and `unlockWithDevice()` maps wrapper, header-tag, and payload failures to `DEVICE_UNLOCK_FAILED`. A `CryptoError("CRYPTO_UNAVAILABLE")` from HKDF or `verifyHeaderSecurityTag()` is therefore masked on those V2 unlock paths.

`packages/ui/src/VaultScreen.tsx` uses argument-free catches for restore, verification, password unlock, Recovery Kit unlock, and device unlock, displaying credential/corruption guidance even when recovery services preserve the outage. Existing coverage in `packages/vault/src/task3.test.ts` checks only Recovery Kit verification and restore. Preserve `isCryptoUnavailable(error)` in `openMasterRoot()`, `unlock()`, and `unlockWithDevice()`; map it to retryable UI guidance; and test wrapper, security-tag, and payload outages across all unlock methods and the UI.

## Automatic lock leaves unsubmitted credentials in UI state

**Severity/confidence: LOW — confirmed.** The `VaultScreen` subscription applies service state with only `setScreenState(nextState)`, while `clearSecrets()` is invoked by manual `lockVault()`. Auto-lock or a CAS-conflict lock unmounts populated password-change, enrollment, restore, or step-up controls without clearing their controlled values, which reappear when those forms remount. Restore/back, password/Recovery Kit unlock, and step-up-method toggles also hide abandoned secret fields without clearing them.

Clear secret state when leaving the current unlocked context and when abandoning or switching credential flows; encrypted BYOS ciphertext can remain. Add UI tests that populate secrets, emit a locked state or switch methods, remount the form, and assert empty values.
