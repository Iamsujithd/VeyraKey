# Task 3 security hardening final review (v4)

One actionable code finding remains after tracing the v3 remediations through the service, UI, crypto adapter, persistence integration, and Task 3 boundaries. Status-changing locks clear secrets, but two abandoned-flow cases remain: device alternatives do not clear an entered password or Recovery Kit, and an authenticated recovery-state change can unmount the verified-vault forms while retaining their inputs. Existing UI tests do not cover either transition followed by failure or remount. **Watch for:** **LOW — confirmed** unsubmitted credentials survive device-method and same-status recovery-form transitions.

**Verdict**: NEEDS_CHANGES

## High-level view

Secret clearing is keyed only to the top-level vault status, while recovery reconciliation can replace the entire unlocked form without changing that status. Device unlock and step-up also bypass the explicit password/Recovery Kit switch handlers, leaving those controlled fields populated when a device ceremony fails or is canceled.

## Device and recovery-form transitions retain abandoned credentials

**Severity/confidence: LOW — confirmed.** `unlockDevice` starts device unlock without clearing `masterPassword` or `recoveryKitInput` (`packages/ui/src/VaultScreen.tsx:409-421`), although the device action remains available beside either locked credential form (`VaultScreen.tsx:744-768`). `deviceStepUp` likewise leaves `stepUpPassword` and `stepUpRecoveryKit` populated before invoking the device credential (`VaultScreen.tsx:449-463`, `1010-1038`). A canceled or failed device ceremony therefore leaves the abandoned secret in the mounted field.

The transition effect depends only on `screenState.status` (`VaultScreen.tsx:231-247`). Reconciliation can publish `recoveryKitVerified: false` while keeping status `unlocked` (`packages/vault/src/service.ts:1252-1254`), replacing the verified-vault forms with the Recovery Kit replacement form (`VaultScreen.tsx:538,910`) without running the clearing effect. Unsubmitted enrollment or password-change fields remain in React state and reappear when verified forms remount.

Clear both relevant fields before each device call and clear all secret state whenever the rendered recovery/security context changes, not only when the top-level status changes. Add rejection-path tests that enter a secret before choosing a device alternative, plus a test that emits `replacement-required` and then `verified` around populated unlocked forms and asserts every remounted secret field is empty.
